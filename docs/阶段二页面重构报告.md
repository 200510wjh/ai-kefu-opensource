### 1. 重建前端主入口

原前端存在大量乱码中文和旧产品表达，容易让企业客户误解产品定位。

本阶段已将主页面重构为“AI 商家运营工作台”结构，保留并复用现有后端接口：

- 登录：`POST /api/auth/login`
- 企业资料：`GET/PUT /api/merchant/profile`
- 总览指标：`GET /api/dashboard/overview`
- 知识库：`GET /api/knowledge`、`POST /api/knowledge/import`、`POST /api/knowledge/upload`
- 会话：`GET /api/conversations`、`GET /api/conversations/{id}`、`POST /api/conversations/{id}/handoff`
- 渠道：`GET /api/channels`、`PUT /api/channels/{channel}`
- Connector：`GET /api/connectors`
- Workflow：`GET /api/workflows/runs`
- AI Engine：`GET /api/ai-engine/status`
- 本机脚本：`GET /api/local-scripts`、`POST /api/local-scripts/{id}/run`
- 商品素材：`POST /api/product-media/pack`

### 2. 固定十个模块

每个模块都只展示真实接口或明确的未启用说明。

#### 企业管理

展示并保存企业资料、行业、营业时间、联系方式、业务介绍、商品服务、价格套餐、优惠活动。

#### 获客中心

读取真实线索池和客服会话中的高意向客户。

没有线索时只显示空状态，不造假数据。

#### AI 客服

展示网页客服接入代码、测试页入口、真人风格回复草稿和会话收件箱。

按钮均对应真实后端接口。

#### CRM

复用真实会话、真实线索、意向分、待人工接管状态。

标签、销售阶段、企业画像属于后续 CRM 深化阶段，当前不放假按钮。

#### 知识库

支持结构化文本导入、文档上传、FAQ 编辑和知识条目列表。

当前明确只支持 txt、md、csv、json；PDF/Word 解析不假装已完成。

#### 商品中心

保留真实商品素材生成接口，支持商品资料、图片上传、主图、详情图、视频预览、上架资料复制。

#### 自动化中心

读取真实本机脚本列表，并把脚本运行结果显示出来。

Workflow 运行记录读取 `/api/workflows/runs`。

#### AI 决策中心

展示 AI Engine 状态，并复用已接入的客服脚本生成能力。

对话总结、风险识别、意向评分、Prompt 生成等统一 AI 能力会在第四阶段继续沉淀。

#### 经营分析

只展示现有真实经营概览指标。

日报、周报、月报和转化效率统计在第十一阶段接入，不放假按钮。

#### 系统设置

展示 Connector 注册表、渠道配置、模式、状态、回调地址、自动回复和人工确认开关。

## 四、假按钮与假数据检查

本阶段处理原则：

- 有真实后端接口的按钮才保留。
- 无后端逻辑的能力只显示说明，不提供可点击操作。
- 空列表显示空状态，不填充模拟客户、模拟订单或模拟线索。
- 登录后数据来自后端，刷新后不会靠前端假数据维持。

仍需后续阶段验证的点：

- CRM 标签、销售阶段、企业画像还未做数据库模型和接口。
- 经营分析日报、周报、月报还未做后端报表接口。
- Connector 目前是注册表状态，不代表所有平台官方 API 已授权。

## 六、进入第三阶段前的架构冲突

第三阶段要求“统一 API 返回格式”。

当前系统已有大量接口直接返回 Pydantic 对象或数组，例如：

- `GET /api/conversations`
- `GET /api/knowledge`
- `GET /api/channels`
- `GET /api/connectors`
- `POST /api/product-media/pack`

如果现在直接把所有接口改成统一格式：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "request_id": "..."
}
```

会破坏当前前端、验收脚本和已部署调用方。

建议选择其一：

### 方案 A：兼容式重构

保留现有 `/api/*` 返回格式，新建 `/api/v1/*` 统一返回格式。

优点：不破坏现有页面和已部署能力。

缺点：短期内会同时存在旧接口和新接口。

### 方案 B：一次性切换

所有现有 `/api/*` 立即改成统一返回格式，并同步修改前端和验收脚本。

优点：接口形态更干净。

缺点：影响面大，容易引入回归，线上部署前必须完整联调。

### 方案 C：只统一新增接口

旧接口不动，从第三阶段开始新增的认证、权限、日志、缓存、数据库模型接口全部使用统一格式。

优点：风险最低。

缺点：系统一致性需要更长时间收敛。

建议采用方案 A。
